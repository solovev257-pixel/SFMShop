# Развёртывание SFMShop

## Подготовка

Используются Python 3.13, Docker Engine и Docker Compose v2 с поддержкой `--wait`.
Зависимости Python устанавливаются из `requirements.txt`. `.env` создаётся из
`.env.example` только при отсутствии файла. Для сервера нужно заполнить собственные
пароли PostgreSQL и RabbitMQ, ключ подписи JWT и при необходимости ключ VseGPT.

На текущем компьютере `venv` и `.env` уже существовали. Пакеты установлены и проверены
через `pip check`. Содержимое `.env` при подготовке решения не просматривалось.
При проверке контейнеров использовался только публичный `.env.example`.

## Выбор размещения

В репозитории есть `docs/hosting_strategy.md`. Указанный в задании
`docs/hosting_comparison.md` отсутствует, поэтому за основу взята существующая стратегия.
Для учебного этапа выбран один VPS с Docker Compose. Ориентир из стратегии —
2–4 vCPU и 4–8 ГБ памяти, достаточность требует нагрузочного тестирования.
Управляемый PostgreSQL позволяет передать резервное копирование и обслуживание
провайдеру. PostgreSQL в Compose подходит для воспроизводимой учебной проверки.
Конкретный провайдер и платный тариф пока не выбраны.

## Запуск

Из корня проекта выполнить

```sh
docker compose --env-file .env -f docker/docker-compose.yml up -d --build --wait --wait-timeout 180
docker compose --env-file .env -f docker/docker-compose.yml ps
```

Приложение доступно по `http://127.0.0.1:8000`. Swagger со списком методов находится
по `/docs`, административная страница по `/admin`. Порт меняется через `APP_PORT`.
На VPS перед приложением нужен reverse proxy с HTTPS, например Nginx или Caddy.
Он принимает внешний запрос и передаёт его на локальный порт приложения.

`POSTGRES_PORT` и `REDIS_EXTERNAL_PORT` задают порты для подключения с компьютера
разработчика. Все опубликованные порты привязаны к `127.0.0.1`. RabbitMQ и MongoDB
доступны контейнерам внутри сети `app_network`.

Образ собирается в два этапа. Сначала устанавливаются библиотеки, затем в итоговый
образ копируются установленные пакеты, `src` и `templates`. Процесс работает
от `appuser`. Проверка здоровья обращается к `/health/ready`.

## Изолированная проверка

```sh
docker compose --env-file .env.example -f docker/docker-compose.yml -p sfmshop-mentor up -d --build --wait
python scripts/check_deployment.py
docker compose --env-file .env.example -f docker/docker-compose.yml -p sfmshop-mentor logs --tail 30 worker
```

Скрипт создаёт вымышленных покупателей и заказ, проверяет вход, остатки товаров,
сохранённый статус и защиту доступа. Он изменяет данные только в проверяемом стеке,
поэтому его запускают на учебной БД. Повторный запуск создаёт новых покупателей
и расходует ещё одну единицу товара.

После проверки стек можно остановить с сохранением данных

```sh
docker compose --env-file .env.example -f docker/docker-compose.yml -p sfmshop-mentor down
```

## Хранение, обновление и восстановление

Именованные тома `postgres_data`, `redis_data`, `rabbitmq_data` и `mongo_data`
сохраняют данные при пересоздании контейнеров. Redis работает с AOF, RabbitMQ
использует постоянные очереди и сообщения. `down --volumes` удаляет тома с данными.

`docker/init.sql` применяется только при создании пустого тома PostgreSQL.
При обновлении существующей базы изменения схемы выполняются отдельно после
резервного копирования. `src/database/migrations.py` — учебная миграция статуса заказа,
она не заменяет создание всей схемы и не создаёт поле пароля в старой таблице users.
Новая учебная база должна инициализироваться через `docker/init.sql`.

Перед обновлением сохранить дамп PostgreSQL через `pg_dump` и проверить восстановление
на отдельной базе. Для приложения использовать версию образа с идентификатором коммита.
После обновления проверить `/health/ready` и основные HTTP-сценарии.
При откате вернуть предыдущий образ, предварительно проверив совместимость схемы БД.

## CI/CD и фактическое состояние

`.github/workflows/ci.yml` выполняет тесты и проверяет порог 81%, затем собирает
контейнеры и запускает сквозной сценарий на GitHub runner. Отчёты покрытия сохраняются
как артефакты. Job `deploy` проверяет контейнерное развёртывание в CI.
Для внешнего сервера потребуются реестр образов, адрес сервера и доступ через
GitHub Secrets. Внешнее развёртывание оставлено опциональным по заданию.

16 ноября 2026 года локальная multi-stage сборка и запуск шести сервисов Compose
успешно проверены. Сквозной сценарий подтвердил healthcheck, регистрацию, вход,
создание заказа, списание остатка, совпадение статуса POST и GET и отказ доступа
к чужому заказу. Использовались вымышленные покупатели и отдельные учебные тома.
Обработчик выполнил задачи, обе очереди RabbitMQ остались без ожидающих сообщений.
В MongoDB подтверждено сохранение 20 событий учебной очереди.
Фактический запуск GitHub Actions требует отправки изменений в репозиторий.
Kubernetes требует отдельного кластера и подготовленных сервисов, его план описан
в `docs/infrastructure_plan.md`.

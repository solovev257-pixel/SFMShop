# Масштабируемая архитектура для SFMShop

Цель: выдерживать 5000+ RPS, пережить вечерние пики выходных и отказ любого одного узла без остановки магазина.

Путь запроса: Клиент → CDN → Балансировщик nginx → API-серверы FastAPI → Redis → PostgreSQL. Долгие операции уходят в RabbitMQ.

## Компоненты:

### Балансировщик нагрузки (nginx)
- Принимает все входящие запросы и раздаёт их между API-серверами.
- Алгоритм Least Connections: запрос уходит на сервер с наименьшим числом активных соединений, поэтому тяжёлый запрос не тормозит остальных.
- Проверяет здоровье серверов (max_fails, fail_timeout) и перестаёт слать трафик на упавший.
- Завершает HTTPS (SSL termination) и ограничивает частоту запросов (rate limiting).
- Балансировщиков два, чтобы он сам не стал единой точкой отказа.

### API-серверы (FastAPI)
- Обрабатывают бизнес-логику: каталог, корзина, заказы.
- Stateless: сессия не хранится в памяти сервера, пользователь определяется по JWT в каждом запросе. Поэтому любой запрос может попасть на любой сервер.
- Базово 5 экземпляров, количество меняется под нагрузку.
- Списки отдаются с пагинацией, ответы каталога с заголовком Cache-Control.

### Кэш (Redis)
- Хранит результаты частых запросов к базе: страницы каталога, карточки товаров, курсы валют.
- Общий для всех API-серверов, поэтому кэш не теряется при перераспределении запросов.
- TTL каталога 5 минут: компромисс между свежестью данных и нагрузкой на базу.
- Дополнительно используется для счётчиков rate limiting.

### База данных (PostgreSQL)
- Master принимает все записи: заказы, оплаты, изменения остатков.
- 2 реплики для чтения забирают на себя запросы каталога и истории заказов.
- Остатки при оформлении заказа читаются только с master (строгая согласованность), каталог можно читать с реплик (согласованность в конечном счёте).

### Очередь сообщений (RabbitMQ)
- Принимает долгие задачи, чтобы API отвечал сразу: отправка писем и СМС, обработка оплат, формирование отчётов.
- Отдельные воркеры разбирают очередь в своём темпе, пики сглаживаются.
- Сообщения, которые не удалось обработать после повторов, попадают в Dead Letter Queue для разбора.

### CDN
- Отдаёт статику (картинки товаров, CSS, JS) из ближайшего к пользователю дата-центра.
- Снимает с API-серверов основную часть трафика по объёму.

## Масштабирование:

### Горизонтальное
- API-серверы: добавить экземпляр, если на один сервер приходится больше 800 RPS или CPU выше 70% дольше 10 минут. Убрать лишние, когда нагрузка падает.
- Реплики PostgreSQL: добавить реплику, если реплики загружены выше 70% по CPU или растёт задержка чтения.
- Воркеры очереди: добавить, если в RabbitMQ больше 10 000 сообщений или очередь растёт быстрее, чем разбирается.
- Redis: перейти на кластер, если память заполнена больше чем на 75%.

### Вертикальное
- PostgreSQL master: увеличить CPU, RAM и диск, если CPU выше 70% или свободного места меньше 20%. Запись разделить между серверами сложно, поэтому master растим вверх.
- Redis: добавить памяти, если начинают вытесняться горячие ключи.

### Подготовка к пикам
- Перед распродажами и вечерами выходных заранее поднимать дополнительные API-серверы.
- Автомасштабирование API по метрикам CPU и RPS (например, Kubernetes HPA).

## Отказоустойчивость:

### Health checks
- `GET /health/live` — процесс жив. Если не отвечает, контейнер перезапускается.
- `GET /health/ready` — доступны база и Redis. Если нет, балансировщик временно не шлёт трафик на этот сервер.
- Проверка каждые 10 секунд, сервер возвращается в ротацию автоматически после восстановления.

### Автоматическое восстановление
- Упавший API-сервер заменяется новым без участия человека.
- При отказе master одна из реплик становится новым master (failover).
- Внешние сервисы (оплата, курсы валют) вызываются с таймаутом, повторами с растущей паузой и запасным вариантом, если сервис недоступен.

### Резервное копирование
- Ежедневный полный бэкап PostgreSQL и WAL-логи для восстановления на любой момент времени.
- Копия бэкапов хранится в другом регионе, срок хранения 30 дней.
- Раз в неделю проверяется восстановление из бэкапа на тестовом сервере.

### Мониторинг и алерты
- Prometheus собирает метрики, Grafana показывает дашборды, логи собираются централизованно, ошибки приложения в Sentry.
- Алерт дежурному, если: доля ошибок 5xx выше 1% за 5 минут, latency p95 выше 500 мс за 5 минут, свободного места на диске меньше 15%, очередь растёт быстрее, чем разбирается.

## Метрики:

### Целевые показатели
- RPS: 5000+ в обычном режиме, запас до 10 000 в пиках.
- Latency: p95 меньше 200 мс, p99 меньше 1 секунды.
- Availability: 99,9% в месяц, это не больше 43 минут простоя.
- Error rate: меньше 0,1% ответов 5xx.
- RTO: восстановление после аварии не дольше 15 минут.
- RPO: потеря данных не больше 5 минут.

### Что смотреть при отклонениях
- Растёт latency p95: проверить долю попаданий в кэш, медленные SQL-запросы, время ответа внешних API.
- Растёт доля ошибок: проверить health checks серверов и доступность базы.
- Растёт RPS: добавить API-серверы по правилам из раздела «Масштабирование».

Архитектура асинхронной обработки заказов для проекта SFMShop
Задачи для очереди

При создании заказа API сохраняет заказ в БД и сразу отвечает пользователю. Всё медленное уходит в очередь и делается в фоне:

send_email — после создания заказа, данные: order_id, user_email. Приоритет низкий, письмо может прийти чуть позже.
update_stock — после создания заказа, данные: order_id, items. Приоритет высокий, от склада зависят продажи.
generate_report — после создания заказа, данные: order_id. Приоритет низкий, отчёт нужен не сразу.
send_push — при смене статуса заказа, данные: order_id, status. Приоритет средний.

Так API отвечает быстро и не ждёт почту, склад и отчёты.

Надежность
Сообщения сохраняются на диск (persistent), поэтому не пропадают, если брокер перезапустится.
Consumer подтверждает задачу (ack) только после выполнения. Если он упал, задача вернётся в очередь.
При ошибке задача повторяется до 3 раз с паузой 1, 2 и 4 секунды.
Если все попытки не помогли, задача уходит в очередь ошибок (dead letter), там её разбирают вручную.
Ошибки пишутся в лог.
Масштабирование
Можно запустить несколько Consumer на одну очередь, брокер сам раздаёт им задачи.
Если очередь растёт, добавляем ещё Consumer.
Следим за длиной очереди, скоростью обработки и количеством ошибок.

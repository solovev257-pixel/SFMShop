# Системный дизайн проекта SFMShop

## Архитектура

### Компоненты
- **FastAPI-приложение** (`src/api/main.py`): роутеры `/api/v1/products`, `/api/v1/orders`, `/api/v1/register`, `/api/v1/login`, `/api/v1/users/me`, `/api/v1/support`; middleware логирует каждый запрос и добавляет заголовок `X-Process-Time`.
- **Зависимости** (`src/dependencies.py`): пул соединений → репозитории → текущий пользователь из JWT. Эндпоинты получают всё через `Depends`.
- **PostgreSQL**: товары, пользователи, заказы и позиции заказов. Доступ асинхронный через пул `asyncpg` (`src/database/async_repository.py`).
- **Redis**: кэш каталога (`src/services/cache_service.py`). Если Redis недоступен, приложение продолжает работать напрямую с БД.
- **Внешний API курсов валют**: асинхронный клиент на `httpx` с таймаутом и повторами (`src/services/exchange_client.py`).
- **Помощник поддержки** (`src/services/support_service.py`): модель только определяет тему вопроса, доступ к заказам проверяет Python-код по id пользователя из токена.
- **Админ-страница** `GET /admin`: вход и управление товарами через `fetch`.

### Масштабирование
- API stateless: пользователь определяется по JWT в каждом запросе, сессии в памяти сервера нет. Поэтому можно запускать несколько экземпляров (`uvicorn --workers N` или несколько контейнеров) за балансировщиком nginx.
- Балансировка: алгоритм Least Connections, health checks через `GET /health/live` и `GET /health/ready`.
- База: сначала вертикальное масштабирование (CPU, RAM, диск); при росте чтения — реплики для запросов каталога, запись только в основную БД.
- Долгие операции (уведомления о заказе, журнал изменений каталога) выполняются как фоновые задачи после ответа; при росте нагрузки переносятся в очередь RabbitMQ.

### Кэширование
- Цепочка: браузер (`Cache-Control: public, max-age=60` на списке товаров) → Redis → PostgreSQL.
- Ключи: `products:list:{limit}:{offset}` для страниц каталога, `products:item:{id}` для карточки товара.
- TTL 5 минут. При создании, изменении и удалении товара и при оформлении заказа кэш каталога сбрасывается.
- Заголовок `X-Cache: HIT/MISS` показывает, откуда пришёл ответ.
- При ошибке Redis кэш отключается на 30 секунд, чтобы не тратить время на заведомо неудачные подключения.

## Метрики производительности
- Целевые: p95 latency каталога < 200 мс, p99 < 1 с; доступность 99,9% в месяц; доля ответов 5xx < 0,1%.
- Время обработки каждого запроса пишется в лог middleware и в заголовок `X-Process-Time`.
- Скрипт `scripts/measure_async_performance.py` сравнивает синхронные запросы по очереди с асинхронными параллельными: для курсов 5 валют и для 30 запросов к `GET /api/v1/products`.

## Компромиссы
- **Модель согласованности:** каталог — согласованность в конечном счёте (допустимо видеть цену с задержкой до 5 минут, зато меньше нагрузка на БД); остатки при оформлении заказа — строгая согласованность: заказ проверяет и списывает остатки в одной транзакции с блокировкой строк (`SELECT ... FOR UPDATE`).
- **TTL кэша и обоснование:** 5 минут — каталог меняется редко, а при изменении через API кэш сбрасывается сразу; TTL страхует от изменений в обход API.
- **Что важнее — latency или throughput:** для покупателя важнее latency каталога и оформления заказа; фоновые задачи (уведомления, журнал) оптимизируются под throughput и не задерживают ответ.
